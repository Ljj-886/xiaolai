## 一、管理后台信息架构（4 个页面共用）

统一「**同一张卡片 = 一条记录**」，层级固定 6 层：

| 层 | 内容 | 要点 |
|---|---|---|
| 1. 身份行 | 缩略图/头像 + 标题/昵称 + 右上状态 tag | tag 用状态色板 |
| 2. 属性行 | 价格/预算 · 分类 · 校区 | `flex-wrap` + `row-gap:4rpx` 防挤压 |
| 3. 关联行 | 卖家（头像+昵称+信用+认证 tag）/ 学校·学号·学历 | 头像需 `binderror` 兜底 |
| 4. 问题区块 `.issue` | 仅在**存在异常字段**时渲染，行式 key-value | 见下表 |
| 5. 页脚 | 时间 + 浏览/收藏/想要 计数 | |
| 6. 操作区 | 按钮 | |

**问题区块 `.issue` 的字段映射：**

| 行 | 字段 |
|---|---|
| 来源 | `offTypeText` |
| 原因 | `reasonText`（先过 `cleanReason()`） |
| 操作 | `auditText` = 操作人 · 时间 |
| 复核 | `recheckAtText` → `recheckDecisionText` |
| 图片 | `imgCheckText` |

**可点击跳转的统一手法**：整卡 `bindtap="goDetail"`，卡内所有按钮/缩略图改 `catchtap`
（阻止冒泡，否则点按钮会同时触发跳转）。

**跳转目标与小程序端保持一致**：商品 → `/pages/detail/detail?id=`；用户 → `/pages/sold/sold?openid=`。

**`offType` 缺失的老「已下架」数据** → 来源兜底显示「已下架（历史数据）」，**不要留空**
（审核人员看到空白来源无法判断去向）。

## 二、商品状态与下架语义

状态全集：`pending / onSale / sold / reserved / off / banned`（**`banned` = 禁售**）

```
发布 → pending（仅「我的商品·审核中」可见）
  ├─ 后台通过 → onSale
  └─ 驳回     → off + offType:'reviewReject'

onSale → 卖出 → sold
       → 买家预留 → reserved
       → 下架/禁售 → off/banned（不硬删，保留可查）
```

**`offType` 来源枚举：**

| 值 | 含义 | `recheck` |
|---|---|---|
| `self` | 卖家自主下架 | `false` |
| `report` | 举报下架 | `true` |
| `admin` | 管理员下架 | `true` |
| `ban` | 管理员禁售 | `true` |
| `imgRisk` | 图片违规 | `true` |
| `reviewReject` | 审核驳回 | — |

**二次审核队列**：`recheck=true` 的进入「待二次审核」。
`admin.recheckGoods({id, decision})`：
- `onSale` —— 重新上架
- `off` —— 维持下架
- `banned` —— 改判禁售

出队并写 `admin_logs`。
后台查询：`admin.listGoods({status:'recheck'|'removed'|'off'|'banned'|...})` + 关键词检索（覆盖下架/禁售原因）。

## 三、首页快速刷新（双层失效，缺一都会等 10s/60s）

管理端改完商品状态后需要**双管齐下**：

1. **服务端** —— 云函数侧跨调破 10s 列表缓存：
   ```js
   cloud.callFunction({ name: 'goods', data: { action: 'markDirty' } });
   ```
2. **客户端** —— 破 60s SWR 节流：
   ```js
   wx.setStorageSync('cm_home_dirty', Date.now());
   ```
   首页 `onShow` 消费并清除该标记。

## 四、图片链路要点

- `<image>` **无法渲染 `cloud://`**，必须由服务端换成 https 临时链接。
- 临时链接**仅 10 分钟**有效 → **一切缓存 TTL 必须 < 6 分钟**。
- 大图缩放用 `imageMogr2`，**必须用 `&` 追加**参数（用 `?` 会导致签名失效）。
- 所有服务端图片都要有 `binderror` 兜底。
- **清「失败标记」时必须同时改变资源地址**，否则会永久空白。

## 六、云开发查询坑（完整版）

### 「或」条件（踩过三次）

```js
// ❌ 静默失效：云开发忽略整个条件，返回多余数据（不报错，最难查）
where.type   = _.or([{type:'sell'}, {type:_.exists(false)}, {type:null}]);
where.campus = _.or([{campus:mySchool}, {campus:_.in(['',null])}, {campus:_.exists(false)}]);

// ✅ 正确：把「或」提成顶层，再与其余条件 _.and 组合
db.collection(C).where(_.and([ where, _.or([...]) ]));
```

等价改写（单字段排除类）：`where.type = _.neq('want')` 更简单且实测有效。
**字段条件只用「值型」命令**：`_.eq / _.neq / _.in / _.gte / _.lte / _.exists`。

**验证方法论（关键）**：现有数据往往「全是同一取值」，此时**过滤失效与生效的结果完全相同，测不出来**。
必须**临时插入一条异值数据**做对照实验，测完立即删除。
`tools/verify_campus_isolation.js` 即「插异值→断言→自清理」的可复用实现。
实例：goods 有 6 条本校 + 插 1 条外校 → 失效写法返回 7（含外校）、正确写法返回 6。

### 其他

- **`count()` 不能与 `_.in()` 聚合**：`where({_openid: _.in(ids)}).count()` 会把同一数字返回给每个 id。
  要分组统计必须 `field({_openid,status}).limit(1000).get()` 后在内存里 reduce。
- **`_.in(['', null])` 匹配不到「字段不存在」的文档** → 老数据兼容必须显式加 `_.exists(false)`。
- **`.limit()` 上限**：客户端 100 / 云函数 1000，**超了静默截断**（统计少算、删除不净）。
- **集合不存在抛 `-502005`** → 读用 `readSafe`、写用 `ensureAdd`（都在 `cloudfunctions/admin`）。

## 七、求购（want）模块

商品 `type: 'want'`（求购）/ `'sell'`（出售，含历史无 type）。
服务端 `isWant` 时：图片选填、价格为「预算」选填、`condition` 强制 `'normal'`、
`originalPrice` 置 null、无图时 `imgCheckStatus='safe'`。

**状态文案分表**（`utils/util.js`）：
- `STATUS_GOODS` —— 在售 / 已售出 / 已下架 / 禁售
- `STATUS_WANT` —— 募集中 / **已达成** / **已关闭** / 已下架

取文案统一用 `goodsStatusText(item)`（自动按 type 选表）。

**求购无成色概念** → 卡片/详情 `condText` 必须置空，不要渲染「正常使用」。

**无图求购**：
- 详情页走 `.hero-want` 占位区（**不要渲染 swiper**，否则计数器显示 `1/0` + 大片白块）
- 卡片走 `.gc-noimg` 卡面（`noCover` 标志），**不要复用 `goods-cover-default.png`**（像裂图）
- 无图时不挂「求购」角标（卡面已有）

**列表分流**：出售用 `type: _.neq('want')`，求购用 `type: 'want'`。

## 九、并发安全：状态流转与计数（2026-09-15 新增）

### 9.1 铁律：**条件更新 + 校验 `stats.updated`**

云开发没有 `findOneAndUpdate`，所以「读—判断—写」必须用**条件更新**来闭合竞态：

```js
// ❌ 错误：两个并发请求都会读到旧状态、都通过校验 → 双写
const o = await db.collection('orders').doc(orderId).get();
if (!['meeting','paid'].includes(o.data.status)) return fail('状态不允许');
await db.collection('orders').doc(orderId).update({ data: { status: 'completed' } });

// ✅ 正确：把状态条件放进 where，用 updated 数判断「谁抢到了」
const upd = await db.collection('orders')
  .where({ _id: orderId, status: _.in(['meeting', 'paid']) })
  .update({ data: { status: 'completed' } });
if (!(upd.stats && upd.stats.updated === 1)) return fail('状态已变更，请刷新后重试', 409);
// ↓ 只有抢到状态的那一次才会执行，天然幂等
await bumpCounts();
```

注意：`status: _.in([...])` 是**值型命令**，可以用在 where 里；
但**绝不能**把 `_.or([...])` 赋给某个字段（会被静默忽略，见第六节）。

### 9.2 已应用的位置

| 位置 | 防的问题 |
|---|---|
| `order.create` | **超卖**：同一商品被并发下单出多个订单 |
| `order.complete` | **计数虚高**：买卖双方同点「完成」→ 计数各 +2 |
| `order.sellerConfirm` / `buyerCancel` / `sellerCancel` | 状态互相覆盖（如买家取消与卖家确认同时发生） |
| `order.checkTimeout` | 超时巡检与人工操作并发 |

### 9.3 释放商品：必须带 `status:'reserved'` 条件

```js
/** 释放商品回「在售」。⚠️ 必须带 status:'reserved' 条件 */
async function releaseGoods(goodsId) {
  await db.collection(COL_GOODS)
    .where({ _id: goodsId, status: 'reserved' })   // ← 关键
    .update({ data: { status: 'onSale', updatedAt: Date.now() } });
}
```

不加这个条件，会把「订单等待期间**已被管理员下架/禁售**（off/banned）」的商品**复活上架**。

### 9.4 计数字段：用「实时统计回写」而非 `_.inc` 累加

```js
// ❌ _.inc 一旦某次写失败或被并发覆盖，计数就永久漂移、越差越多
await goods.update({ data: { favCount: _.inc(1) } });

// ✅ 用集合真实条数回写 → 天然自愈（连历史漂移一起纠正）
const c = await db.collection('favorites').where({ goodsId }).count();
await goods.update({ data: { favCount: c.total } });
```

配套：收藏/想要记录用**确定性 `_id`**（`openid_goodsId`）写入，
并发重复写入只会落到同一文档，不会产生两条。
（注意 `count()` 只能用于**单字段**过滤；不能与 `_.in()` 聚合，见第六节。）

### 9.5 权限与内部动作

- **管理员权限不可横向扩散**：授予/撤销管理员必须限 `isWhitelistAdmin(openid)`，
  只校验 `requireAdmin` 会让「被提权过的普通管理员」再提权任意人。
- **客户端调用必带 OPENID，跨函数内部调用不带** —— 可据此鉴权内部动作：
  ```js
  async markDirty(_event, openid) {
    if (openid) {  // 有 OPENID = 客户端调用 → 必须是管理员
      const u = await db.collection(COL_USER).where({ _openid: openid }).limit(1).get();
      if (!u.data?.[0]?.isAdmin) return fail('无权限', 403);
    }
    // openid 为空 = admin 云函数跨函数调用，放行
  }
  ```
- **纯定时器动作**在派发处直接拒绝客户端：`if (event.action === 'pendingImgCheck') return fail('禁止直接调用', 403)`

### 9.6 后台关键词搜索必须在 DB 层过滤

```js
// ❌ 先 skip+limit 取 20 条再内存 filter → 只搜「当前页」，库里超一页的数据永远搜不到
const r = await query.skip(...).limit(20).get();
r.data = r.data.filter(u => u.nickName.includes(k));

// ✅ DB 层检索：正则转义 + 顶层 _.or 与其余条件 _.and 组合
const re = db.RegExp({ regexp: escapeRegex(kw), options: 'i' });
query = query.where(_.and([where, _.or([{ title: re }, { desc: re }])]));
```

`escapeRegex` 把 `.` `*` `(` 等正则元字符转成字面量（也可防 ReDoS）：
```js
String(s == null ? '' : s).replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
```
