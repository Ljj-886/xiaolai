## 图片裂图根因（控制台 `[渲染层网络层错误] Failed to load image`）

用户贴出控制台报错后，逐层排查得到**两个真实根因**。这一段是本项目图片问题的权威结论。

### 根因 1（主因）：临时图链**10 分钟就过期**，而首页把它当缓存长期持有

**官方结论（我此前注释写「2 小时有效」是错的）**：`cloud.getTempFileURL` ——
「**公有读**的文件获取的链接不会过期，**私有读**的文件获取的链接**十分钟**有效期」。

实测吻合：链接年龄 5 分钟 → 200；**28 分钟 → 403**。用户控制台里 4 条失败 URL 的 `sign`
（`296ab87…/88f60cdd…/9b23eb5…/61dea8a…`，`t=1789124089`）与首页 storage 缓存
`cm_home_list_v1` 里的 cover **完全一致**，真凶即此。

**为什么会一直裂**：首页 SWR 把整份列表（含临时图链）存进 storage；
可「数据没变就跳过 setData」的签名去重**只比对 `_id` 序列**，命中后还刷新缓存时间戳 `at`
→ 页面永远抱着那批已 403 的旧图链，缓存也永远不过期。

**修复（`pages/index/index.js`）**：
1. 缓存新增字段 `urlAt`（从 cover 的 `t` 参数取链接签发时间）；
2. `_hydrateCache` 要求 `Date.now() - urlAt < URL_SAFE_MS(6min)`，否则不秒开、直接走网络；
3. 去重跳过 `setData` 的前提增加「页面正在用的图链仍新鲜」，否则必须 `setData` 换新链接；
4. `onShow` 起 6 分钟定时器换链、`onHide` 停掉（防长时间停留后裂图）。

**连带修复（`cloudfunctions/goods/index.js`）**：实例级 `_urlCache` 的 `URL_CACHE_TTL`
原为 **30 分钟**，比链接自身 10 分钟有效期还长 → 会把快过期/已过期的链接发出去。改为 **3 分钟**。

**`maxAge` 不可靠（实测）**：`maxAge:86400` 返回的地址与默认**完全相同**（`sign`/`t` 一致），
`maxAge:1` 也不会提前失效。不要靠它延长有效期。
（若要彻底不过期，只能把云存储权限改为「所有用户可读」——但这会让认证凭证/聊天图也公开，**不做**。）

### 根因 2：原图是 4~6MB 的 2560×1440 PNG，渲染层扛不住

`[渲染层网络层错误] Failed to load image` + `net::OK` = 网络没问题、**是渲染/解码层失败**。
实测这些 cover 单张 4286.7KB / 5763.2KB，`wx.getImageInfo` 能解码但 `<image>` 渲染层报错。

**根因**：发布页虽有压缩（`sizeType:['compressed']` + `wx.compressImage`），但
`wx.compressImage` 的 quality **只对 JPG 生效，PNG 会原样保留** → 用户选 PNG 截屏就 5MB 原样上传。

**零迁移解法（已实施）**：在临时 URL 末尾**用 `&` 追加** COS 图片处理参数（数据万象 imageMogr2）：

| 后缀 | 结果 |
|---|---|
| 无 | image/png **4286.7KB** |
| `&imageMogr2/thumbnail/1080x/format/jpg/quality/80` | image/jpeg **52.2KB**（≈1/82） |
| `&imageMogr2/thumbnail/750x/format/jpg/quality/75` | image/jpeg **25.7KB** |
| `?imageMogr2/...`（**覆盖**查询串） | **403 签名失效** ❌ |

**不用动存量文件、不用重新上传**。已加到 4 个云函数的统一助手 `imgThumb(url, width, quality)`：
`goods`（列表 750 / 详情 1280 / 头像 200）、`user`（750/头像 200）、`chat`（图 1280、头像 200）、
`order`（750）。`format/jpg` 会丢透明通道，商品图/头像无碍。

- 涉及「带签名/会过期的资源」，**一切缓存 TTL 都必须小于资源有效期**，且要问自己：
  「这个缓存过期时会自动失效吗？」
- 排「图片不见了」先做**分流**：是 `cloud://` 没解析（根因 A），还是链接 403 过期（根因 B）——
  取 4 条失败 URL 的 `t` 参数一算年龄即可判定。

## 修复：「发布后商品不显示，只提示发布成功」（不是 bug 的部分 + 真 UX 缺口）

**用户反馈**：发布后商品不显示，只有「发布成功」提示，怀疑没数据。

**先查数据（关键）**：商品**确实写进库了**，只是卡在 `status: 'pending'`（待审核）。
`admin.stats` → `goods:12, onSale:7, pendingGoods:2`；两条 pending 就是刚发布的
（`6ecb83 "32313"`、`31eb60 "测试封面"`），`user.myGoods` 不传 status 能看到、cover 也已解析。

**真正的缺口（UX）**：
1. 商品先进「待审核」，首页只返回 `onSale` → 首页看不到（设计如此）；
2. 「我的商品」tab 只有 在售/已售/已下架，**`pending` 在前端没有任何入口可见**；
3. `utils/util.js` 的 `STATUS_GOODS` **缺 `pending` 映射** → 商品卡角标渲染成空白；
4. 发布成功后只弹「发布成功」就跳首页 → 用户必然以为没保存。

**修复（全前端，无需部署云函数）**：
- `pages/sold/sold.js`：自己视图新增「审核中」tab（看他人主页不加）；
- `pages/sold/sold.wxml`：审核中页加说明条 + 空状态按 tab 区分；
- `pages/publish/publish.js`：成功后改弹「已提交审核」说明，并 `reLaunch` 到
  `/pages/sold/sold?status=pending` 让用户立刻看到刚提交的商品；
- `utils/util.js`：`STATUS_GOODS` 补 `pending:{text:'审核中',cls:'tag-warn'}`；
- `pages/admin-goods/admin-goods.js`：后台仍显示「待审核」，与它的 tab 名一致。

**审核链路（已确认可用）**：发布 → `pending` → 后台「商品管理·待审核」点「通过上架」
（`admin.reviewGoods pass:true` → `status:'onSale'`）/「驳回」（→ `'off'` + `offReason`）。

**验证**：
- `tools/verify_publish_flow.js`（A 部分）与 `tools/verify_review_chain.js` **9/9 通过**：
  发布→pending→审核中可见→不在首页→通过→onSale→**首页可见**；驳回→off+原因；测试数据 0 残留。
- 全量回归 **21/21 正常**。截图 `tools/_pf_pending.png`（审核中 tab 正常）。
- 踩坑：`goods.publish` 偶发 `cloud.callFunction:fail -404006 empty poll result`（云调用中断），
  加了重试即可（发布链路含 seccheck 较慢）；**失败也可能已在服务端成功**，务必用标题标记 + 前置/后置清理孤儿数据。

**文档**：`docs/发布与审核流程说明.md`（含状态流转表与「是否保留先审后发」的取舍说明）。

## 修复：管理后台整片裂图（admin 是唯一漏做 URL 解析的云函数）

**现象**：控制台 `[渲染层网络层错误] Failed to load image <URL>` + `net::OK`，
**`From server 127.0.0.1`**（本地代理）——与之前 CDN 403 的 `From server 171.105.192.xxx` 特征不同，
据此可区分「空 src / 本地路径」与「远端链接失效」。

**定位（方法论升级，很重要）**：`grep getTempFileURL` 只能找到**已经做了转换**的地方，
**测不出「完全没调用它」的函数** —— 这正是 `admin` 被漏掉的原因：
`goods/user/chat/order` 都做了，唯独 `admin` 没做。于是：
- `admin.listGoods` 的 cover/images 是原始 `cloud://` → **后台「商品管理」12 张缩略图全裂**；
- `admin.pendingReports` 的举报凭证图同样未解析；
- `admin.listUsers` 头像含 `wxfile://` 失效临时路径（页面暂未渲染，属隐患）；
- `admin.getUserDetail` 的 avatarUrl / verifyApply.evidence 未解析。

改用**「数据层图片体检」**定位：挨个拉取所有接口，把每个图片字段归类为
https / cloud / http / wxfile / EMPTY，只允许 https。
新增 `tools/audit_images.js` 做这件事（覆盖 goods/user/chat/order/**admin** 全部接口）。

**修复**（`cloudfunctions/admin/index.js`，已部署 11.5KB）：新增
`imgThumb()` / `resolveImgs(fileIds, width)` / `cleanAvatar()` 三个助手，
接入 `listGoods`、`pendingReports`、`listUsers`、`getUserDetail`（后台 1080、头像 200）。

**顺带修复**：`goods-card` 无封面时兜底是空串 → `<image src="">` 也报同样的错。
项目里其实**早就有** `images/goods-cover-default.png` 占位图却没人引用，
现已在 `goods-card` 增加 `defaultCover` 作为最终兜底（库中 `acb0e6「有没有书」` 就是无图商品）。

**验证**：`tools/verify_admin_imgs.js` **7/7**：后台 cover 11/11 转 https + 带 imageMogr2、
实际请求全 200（25.4/84.2/52.2/102.6/102.6 KB）、images 11/11、用户头像 0 异常；
全量回归 **21/21**。

**踩坑**：
- `mp.reLaunch` 到 `/pages/admin-goods` 偶发抛 `Uncaught [object Object]` 并冲掉自动化连接；
  且 `mp.screenshot` 在该页抓不下来。真实路径（`navigateTo`）正常 → 属自动化工具限制，
  改以**数据层校验**（后台渲染的 cover 已是合法 https + 实际请求 200）替代截图。
- `nav-bar` 组件已确认无问题（只在用户点击时才 navigateBack）。

**文档**：已把本轮追加到 `docs/图片裂图修复说明.md`（含「grep getTempFileURL 测不出没调用的函数」这条方法论教训）。
