# 图片裂图（Failed to load image）修复说明

> 现象：控制台大量报 `[渲染层网络层错误] Failed to load image ...`，页面图片变成空白灰块（用户反馈「我的图片不见了」）。

按「先定位、再改、最后量化验证」的方式排查后，确认**三个叠加的真实根因**（不是一个）。以下按影响面排序。

---

## 根因 1（主因）：临时图链 **10 分钟就过期**，而首页把它当缓存长期持有

### 关键事实（官方文档，此前被误判）

> `cloud.getTempFileURL`：**公有读**的文件获取的链接**不会过期**，**私有读**的文件获取的链接**十分钟**有效期。

项目此前在代码注释里写成「临时图链 2 小时有效」，据此把客户端缓存有效期设为 30 分钟 —— **这是错的**。

实测完全吻合：链接签发后 **5 分钟 → 200**，**28 分钟 → 403**。

### 铁证

用户控制台里 4 条失败 URL 的 `sign` 与首页 storage 缓存 `cm_home_list_v1` 里的 `cover` **逐字一致**：

| 控制台报错的 URL | 缓存里的 cover | 链接年龄 | 结果 |
|---|---|---|---|
| `...&sign=296ab87...&t=1789124089` | 同一条 | 1666 秒（28 分钟） | **403** ❌ |
| `...&sign=88f60cdd...&t=1789124089` | 同一条 | 1666 秒 | **403** ❌ |
| `...&sign=9b23eb5...&t=1789124089` | 同一条 | 1666 秒 | **403** ❌ |
| `...&sign=61dea8a...&t=1789124089` | 同一条 | 1666 秒 | **403** ❌ |
| 新拉取的同名文件 | — | 193 秒 | **200** ✅ |

### 为什么「一直裂、不会自愈」

首页为了性能做了 SWR 缓存：把**整份列表**（其中 `item.cover` 就是临时图链）存进 storage。
而「数据没变就跳过 setData」的签名去重**只比对 `_id` 序列**，命中之后还会刷新缓存时间戳 `at` —— 于是：

- 页面**永远抱着那批已 403 的旧图链**；
- 缓存**永远不过期**（因为 `at` 每次都被刷新）。

这就是「用着用着图片就没了」的完整解释。

### 修复（`pages/index/index.js`）

1. 缓存新增字段 `urlAt`（从 cover 的 `t` 参数取链接签发时间）；
2. `_hydrateCache()` 要求 `Date.now() - urlAt < URL_SAFE_MS(6min)`，否则**不秒开**、直接走网络取新链接；
3. 「跳过 setData」的前提增加**「页面正在用的图链仍新鲜」** —— 否则即使商品没变也必须 `setData` 换新链接；
4. `onShow` 起 6 分钟定时器换链、`onHide` 停掉（防止用户长时间停留在首页后裂图）。

### 连带修复（`cloudfunctions/goods/index.js`）

云函数有一个实例级临时链接缓存 `_urlCache`，其 `URL_CACHE_TTL` 原为 **30 分钟**，
**比链接自身 10 分钟的有效期还长** → 会把「快过期 / 已过期」的链接发给客户端。已改为 **3 分钟**。

### 补充：`maxAge` 参数**不可靠**（实测）

| 传参 | 返回的地址 |
|---|---|
| 默认 | `...?sign=cad8dc6d...&t=1789125909` |
| `maxAge: 86400` | `...?sign=cad8dc6d...&t=1789125909`（**与默认完全相同**） |
| `maxAge: 1` | `...?sign=f5a4ee7f...&t=1789125910`（且 12 秒后仍 200） |

→ **不要靠 `maxAge` 延长有效期。** 若要彻底不过期，只能把云存储权限改为「所有用户可读」，
但这会让**学生认证凭证、举报凭证、聊天图片**也变为公开可读 —— 隐私风险不可接受，**故不做**。

---

## 根因 2：`user.myGoods` 漏做 `cloud:// → https` 解析

`pages/sold/sold.js` 的「自己」视图走 `user.myGoods`，看他人主页走 `goods.list`（已解析）——
而 `myGoods` **完全没有** URL 解析逻辑，导致「我的商品」整页裂图。

| 数据源 | 使用页面 | 修复前 |
|---|---|---|
| `goods.list`（light） | 首页 / 分类 / 搜索 / 他人主页 | ✅ 只解析封面 |
| `goods.detail` | 商品详情 | ✅ 解析 cover + images |
| `myFavs` | 我的收藏 | ✅ 只解析封面 |
| `chat` / `order` | 聊天图 / 订单快照 | ✅ |
| **`myGoods`** | **我的商品 / 我的求购** | ❌ **完全不解析** |

**修复**：批量把列表 `cover` 转 https（网格只展示封面，故只解析封面），
并顺带补上前端一直在传、后端一直没收的 `category` 参数（此前「我的商品」分类筛选是失效的）。

---

## 根因 3：原图是 4~6MB 的 2560×1440 PNG，渲染层扛不住

`[渲染层网络层错误] Failed to load image` 后面跟着 `net::OK` —— **网络层没问题，是渲染/解码层失败**。

实测这些图片单张 **4286.7KB / 5763.2KB**，`wx.getImageInfo` 能解码，
但 `<image>` 渲染层对超大图不稳定（也是首屏图片慢的主因）。

**为什么会出现这么大的原图**：发布页虽有压缩（`sizeType:['compressed']` + `wx.compressImage`），
但 **`wx.compressImage` 的 quality 只对 JPG 生效，PNG 会原样保留** —— 用户选一张 PNG 截屏就 5MB 原样上传。

### 零迁移解法：URL 直接挂图片处理参数

在 `getTempFileURL` 返回的临时 URL 末尾**用 `&` 追加** COS 图片处理参数即可：

```
https://xxx.tcb.qcloud.la/goods/a.png?sign=xxx&t=xxx&imageMogr2/thumbnail/1080x/format/jpg/quality/80
```

| 后缀 | 返回 | 体积 |
|---|---|---|
| 无 | image/png | **4286.7 KB** |
| `&imageMogr2/thumbnail/1080x/format/jpg/quality/80` | image/jpeg | **52.2 KB**（≈ 1/82） |
| `&imageMogr2/thumbnail/750x/format/jpg/quality/75` | image/jpeg | **25.7 KB** |
| `&imageslim` | image/png | 1597.8 KB（效果一般） |
| `?imageMogr2/...`（**覆盖**查询串） | — | **403 签名失效** ❌ |

**不用动存量文件、不用重新上传、不用跑迁移任务**，只在生成 URL 时加个后缀。

已封装为统一助手 `imgThumb(url, width, quality)` 并接入 4 个云函数：

| 云函数 | 场景 | 尺寸 |
|---|---|---|
| `goods` | 列表封面 / 详情图 / 卖家头像 | 750 / 1280 / 200 |
| `user` | 我的商品 / 收藏封面 / 头像 | 750 / 200 |
| `chat` | 聊天图片 / 会话头像 | 1280 / 200 |
| `order` | 订单快照封面 | 750 |

> 注意：`format/jpg` 会把 PNG 转 JPEG，**丢失透明通道** —— 商品图与头像无碍；若将来有需要透明的场景需另行处理。

## 留给后续的注意事项

- **临时链接只有 10 分钟有效期。** 以后任何缓存图片链接的地方（云函数实例缓存、storage、globalData），
  TTL 都必须显著小于 10 分钟，并确认「缓存过期时会自动失效」。
- **不要在注释里写没验证过的常量假设** —— 这次的「2 小时有效」直接导致缓存 TTL 定错，是本次事故的放大因素。
- **排「图片不见了」先分流**：取失败 URL 的 `t` 参数算年龄即可判定是「没解析成 https」还是「链接已过期」。

# 追加修复：管理后台整片裂图 + 空封面商品占位

## 现象

控制台出现 `[渲染层网络层错误] Failed to load image <URL>` + `net::OK`，
且 **`From server 127.0.0.1`**（本地代理，与之前 CDN 403 的 `From server 171.105.192.xxx` 特征不同）。

## 根因 1：`admin` 云函数是唯一漏做 URL 解析的函数

之前修图片问题时用 `grep getTempFileURL cloudfunctions/` 排查 —— 但这个手法**只能找到已经做了转换的地方，
测不出「完全没调用它」的函数**。结果 `admin` 被漏掉了：

| 云函数 | 修复前 |
|---|---|
| `goods` / `user` / `chat` / `order` | ✅ 已解析 |
| **`admin`** | ❌ **未解析** |

受影响的后台数据：

| 接口 | 字段 | 后果 |
|---|---|---|
| `admin.listGoods` | `cover` / `images` | **商品管理页 12 张缩略图全部裂图** |
| `admin.pendingReports` | `images`（举报凭证图） | 举报 tab 的凭证图裂图 |
| `admin.listUsers` | `avatarUrl` | 含 `wxfile://` 失效临时路径（页面暂未渲染，属隐患） |
| `admin.getUserDetail` | `avatarUrl` / `verifyApply.evidence` | 认证凭证图未解析 |

**修复**（`cloudfunctions/admin/index.js`）：新增 `imgThumb()` / `resolveImgs()` / `cleanAvatar()` 三个助手，
在 `listGoods`、`pendingReports`、`listUsers`、`getUserDetail` 里统一做
`cloud:// → https` + `imageMogr2` 缩放（后台用 1080，头像 200），并清理失效临时头像路径。

## 根因 2：无封面商品渲染 `<image src="">`

`goods-card` 的兜底是 `item.cover || item.images[0] || ''` —— 最后回退成**空串**，
`<image src="">` 同样会报 `Failed to load image`（且地址是 `127.0.0.1`）。
库里 `acb0e6「有没有书」` 就是这种无图商品，在首页/我的商品里留白。

**修复**：项目里其实**早就有** `images/goods-cover-default.png` 占位图，只是没人引用。
现在 `goods-card` 增加 `defaultCover` 并作为最终兜底。

## 实测验证（真机）

| 检查项 | 结果 |
|---|---|
| `admin.listGoods` 的 cover 转 https | ✅ 11/11 |
| cover 带 `imageMogr2` | ✅ 11/11 |
| 后台缩略图实际请求 | ✅ 全部 **200**，体积 **25.4 / 84.2 / 52.2 / 102.6 / 102.6 KB** |
| `admin.listGoods` 的 images 转 https | ✅ 11/11 |
| `admin.listUsers` 头像无失效路径残留 | ✅ 3 个用户，异常 0 |
| 全量页面回归 | ✅ **21/21 正常** |

- `cloudfunctions/admin/index.js`（已 CLI 部署，11.5 KB）
- `components/goods-card/goods-card.js` / `.wxml`（占位图兜底）

## 方法论教训（重要）

**`grep getTempFileURL` 是不够的** —— 它测不出「压根没调用」的函数。
正确做法是**做一次数据层体检**：挨个拉取所有接口，检查每个图片字段的形态
（只允许 `https://`，出现 `cloud://` / `http://` / `wxfile://` / 空值都要警惕），
并且**一定要覆盖后台接口** —— 后台页面平时没人看，裂图最不容易被发现。
