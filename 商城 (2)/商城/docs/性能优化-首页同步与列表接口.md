# 性能优化：商品上架同步与列表接口

> 目标：缩短「商品上架后 → 首页可见」的延迟，提升各模块接口响应速度与页面刷新效率，整体降低用户等待时间。

## 一、定位到的主要性能瓶颈

| # | 瓶颈 | 位置 | 影响 |
|---|---|---|---|
| 1 | **审核流 → 首页可见延迟（业务层，最大）** | `cloudfunctions/goods` `publish` 写入 `status:'pending'`；首页只查 `onSale` | 新品须管理员 `reviewGoods` 通过后（onSale）才出现在首页。属人工审核，非代码同步延迟（保留既有审核约定，仅优化「onSale 之后」的技术同步） |
| 2 | **首页 SWR 60s 新鲜节流阻断刷新** | `pages/index/index.js` `CACHE_FRESH_MS=60s` | `onShow` 在 60s 内直接跳过重拉，商品 onSale 后浏览用户最多等 60s + 重新进首页才看到 |
| 3 | **`goods.list` 云函数冷请求 ~800ms** | `cloudfunctions/goods` `decorate` 每请求并行 3 路 DB + `getTempFileURL`（~380ms） | 无结果缓存，每次重算；首页/分类/搜索/我的商品每次 onShow 都付出该成本 |
| 4 | **调用者学校每次重查** | `list` 每请求 `db.collection(users).where(_openid).limit(1)` | 多校隔离前置查询，~30-50ms，可缓存 |
| 5 | **无数据库复合索引** | `goods` 集合 | 列表查询在大表上可能全表扫描，数据量大时延迟陡增 |

## 二、已实施的代码层优化

### 1. `goods.list` 服务端结果缓存（最高价值）— `cloudfunctions/goods/index.js`
- 模块级 LRU `Map`：`_listCache`，key = `openid | _openid | type | category | keyword | condition | minPrice | maxPrice | sort | page | pageSize | status | school`，**TTL 10s，上限 200 条**。
- 命中直接返回，**跳过 DB + `decorate`**，响应从 ~800ms 降到 ~10-50ms。
- key 含 `openid`/`_openid` → 收藏/想要态、学校隔离天然正确，**不会串用户**。
- 缓存内嵌的封面临时链接随 `getTempFileURL` 的 3min 缓存一起 fresher，且客户端 6min 换链兜底，不会裂图。

### 2. 写入即失效 — `cloudfunctions/goods/index.js`
- `publish / update / setStatus / remove` 成功后置模块级 `_goodsListDirtyAt = Date.now()`。
- `list` 在「刚写过」的 10s 窗口内**强制跳过缓存**，保证新上架 / 改价 / 上下架**立即可见**，不被缓存挡住。
- 跨实例不共享：多实例部署下某浏览者至多看到 10s 内旧列表，可接受（客户端还有 60s SWR + 6min 换链兜底）。

### 3. 调用者学校缓存 — `cloudfunctions/goods/index.js`
- `callerSchool(openid)`：按 openid 缓存 60s，省去列表每请求的一次 users 查询。

### 4. 首页脏标记失效 — `pages/index/index.js`
- `onShow` 读取 `cm_home_dirty`：若标记比当前缓存新 → **跳过 60s 节流强制重拉**，让「我刚发布 / 上架的商品」回首页**立刻可见**；消费后清除标记。

### 5. 写入口写入脏标记（触发首页强制刷新）
- `pages/publish/publish.js`：发布成功、编辑保存后写入 `cm_home_dirty`。
- `pages/sold/sold.js`：`setStatus`（上/下架）后写入。
- `pages/detail/detail.js`：卖家上/下架后写入。

## 三、仍需手动完成的配置项（数据库复合索引）

云函数代码无法创建索引，需在**云开发控制台 → 数据库 → goods 集合 → 索引**添加（或用 `tcb` CLI），让列表走索引而非全表扫描：

| 索引字段（顺序敏感） | 用途 |
|---|---|
| `status`(升序) + `campus`(升序) + `createdAt`(降序) | 首页信息流（本校在售，按时间倒序） |
| `status`(升序) + `_openid`(升序) + `createdAt`(降序) | 我的商品 / 他人主页（按状态+卖家） |
| `status`(升序) + `category`(升序) + `createdAt`(降序) | 分类列表（按分类筛选） |

> 唯一索引不要勾。首条建议索引覆盖 90% 的首页/分类流量，优先级最高。

## 四、部署与验证

1. **必须重新上传部署 `goods` 云函数**（右键 `cloudfunctions/goods` → 上传并部署：云端安装依赖），否则服务端缓存不生效。
2. 小程序端 `Ctrl+R` 重新编译。
3. 验证清单：
   - 发布 → 审核通过（onSale）后，回到首页能在 60s 内（本机写过则即时）看到新商品；
   - 分类/搜索/我的商品 切换 tab 的刷新明显变快（命中服务端缓存）；
   - 全量页面 26/26、全功能 59/59 零报错零警告。

## 五、效果预期

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 首页冷拉（首屏） | ~800ms | ~800ms（首屏仍需 DB；之后同实例命中缓存 ~50ms） |
| 分类/搜索 重复切换 tab | ~800ms/次 | 命中缓存 ~50ms（10s 内） |
| 本机刚发布/上架回首页 | 最多等 60s 才刷新 | 即时强制刷新，立即可见 |
| 大表列表查询 | 可能全表扫描 | 走复合索引 |
