# 性能优化说明（首页图片 / 私聊消息 / 全局响应）

> 日期：2026-09-11
> 方式：先读源码定位真实瓶颈，再针对性改造，最后用真机（miniprogram-automator）量化验证。

---

## 一、三处瓶颈与对应方案

### 1. 首页商品图片加载慢

**瓶颈**
- 后端 `goods.decorate()` 在列表场景把**每个商品的全部 images（最多 9 张）+ cover** 都拿去调
  `cloud.getTempFileURL`。而首页网格只用 `cover` —— 20 个商品 × 多图 = 一次上百个 fileID 白转换
  （`getTempFileURL` 单次约 380ms，是首屏图片慢的主因）。
- 首页每次 `onShow` 都全量重拉列表并整表 `setData`，导致 `<image>` 被重新赋值 → 图片反复重新加载（"闪一下"）。

**方案**
- `goods.decorate(list, openid, { light })`：列表 `light=true` 时**只解析 cover**；详情页 `light=false` 才解析全部图。
  `goods.list` 传 `{ light: true }`，`user.myFavs` 同样只解析封面。
  未解析的 images 保留原始 `cloud://` fileID（`<image>` 可同环境直接渲染），详情页再解析。
- 前端首页加 **SWR 缓存**：用 storage 缓存列表（`cm_home_list_v1`），进入先秒开缓存再后台刷新；
  **列表签名（`_id` 序列）去重** —— 数据没变就跳过 `setData`，避免重渲染与图片重载；60s 内新鲜缓存直接跳过请求。
- 新增**骨架屏**（shimmer），首屏无缓存时占位，提升"快"的感知。

### 2. 用户私聊消息发送慢（文本 / 表情 / 图片）

**瓶颈**
- `chatroom.onShow` 起 `setInterval(loadMessages, 5000)`，**每 5 秒全量拉 30 条 + 全量 `setData`**。
- `_send` 要「等云函数往返 → 再 `loadMessages` 一次往返」才见到消息 → 发送感知慢。
- 图片发送是「压缩 → 上传 → send → 再 reload」4 段串行。
- 页面切走（onHide）后定时器不停，后台空转。

**方案**
- 后端 `chat.messages({ ..., since })` 支持**增量拉取**（只返回 `createdAt > since` 的新消息），
  无新消息时不写未读、不返回；`chat.send` 返回真实 `_id`。
- 前端 **乐观发送**：文本/表情/图片**点击即上屏**（pending 半透明态），成功后用返回的真实 `_id` 原地替换，
  不再二次全量拉取；失败标红提示。
- 轮询改**增量**（`since`），无新消息零 `setData`；新增 `onHide` 暂停轮询；`_sending/_loadingMsgs` 防并发竞争重复。

### 3. 全局响应（页面切换 / 数据请求 / 交互）

**方案**
- 首页 SWR 缓存 + 签名去重（见上）显著降低页面切换时的重复请求与渲染。
- 项目已启用 `app.json` 的 `lazyCodeLoading: "requiredComponents"`（按需注入组件）。
- 聊天轮询由"全量"改"增量"，后台不再空转。

## 二、实测数据（真机 automator）

| 项目 | 优化前 | 优化后 |
|---|---|---|
| `chat.messages` 轮询 | 每 5s 全量 30 条 + 全量 setData | 增量：689ms/30条 → **431ms/0条**，无新消息**零 setData** |
| `chat.send` | 不返回消息 id（需再拉一次全量） | **返回真实 `_id`**，可原地替换，省一次全量拉取 |
| 首页图片 URL 解析 | 每件解析 cover + 全部 images | **只解析 cover**；多图商品非封面图保持 `cloud://`（已验证） |
| 首页二次进入 | 每次全量重拉 + 重渲染 | 命中缓存跳过请求，数据未变**跳过 setData**（不闪、不重载图） |

**决定性验证**（`tools/live_proof_light.js`）：临时发布一个多图商品 → 断言
`cover=images[0]` 被解析为 `https`、`images[1]` 保持 `cloud://` → **PASS**，随后删除临时商品（`removed:true`，零残留）。

**页面回归**：`tools/live_all_pages.js` → **21/21 全部正常，0 报错**。

## 四、追加修复：「我的商品」页图片裂图（回归）

**问题**：优化上线后，用户反馈「我的图片不见了」。真机截图确认 `pages/sold/sold`（我的商品）网格内
图片全部为灰色空块。

**根因**：本次「列表只解析封面」的优化，把 `goods.list` / `myFavs` 都改成了只解析封面，但
`cloudfunctions/user/index.js` 的 **`myGoods` 被遗漏** —— 它原本就完全没有 `cloud:// → https` 的转换逻辑。
而小程序 `<image>` 组件无法直接渲染 `cloud://` 协议，必须由服务端换成临时 https 链接，所以该页整片裂图。
（看他人主页走的是已修复的 `goods.list`，因此只有「我的商品」这一处出问题。）

**修复**：`cloudfunctions/user/index.js` → `myGoods`
- 批量把本页商品的 `cover` 通过 `getTempFileURL` 转 https（网格只展示封面，故只解析 cover，与 light 模式一致）；
- 顺带补上前端一直在传、后端始终未接收的 `category` 参数 → 「我的商品」的分类筛选由失效恢复为生效。

**验证结果**

| 检查项 | 结果 |
|---|---|
| `goods.detail` 的 cover + images 全部 http(s) | ✅ |
| `myGoods` cover 全部 https、残留 `cloud://` 0 条 | ✅ 4/4 |
| `myGoods` 分类筛选 `category=bike` 命中且全匹配 | ✅ 1 条 |
| 全量页面回归（21 页） | ✅ 21/21 |
| 「我的商品」页真机截图 | ✅ 封面正常显示 |

**本次改动文件**：`cloudfunctions/user/index.js`（已 CLI 部署）
