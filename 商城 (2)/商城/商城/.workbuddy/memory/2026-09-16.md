### 1. 浏览量去重（goods.detail）

- 原实现：`detail` 无条件 `viewCount: _.inc(1)` —— 同一用户反复进出详情页、或脚本高频调用
  都会虚增浏览量，进而抬高「hot」排序（`viewCount desc`）。
- 修法：新增 `viewLogs` 集合 + `bumpView()` helper，用**确定性 `_id`（`openid_goodsId`）**记「谁看过」，
  首次才 `_.inc(1)`，重复查看不再累计。语义从「点了多少次」变为「多少不同的人看过」，更合理。
- 配套：`goods` 新增 `ensureSet()`（幂等 set + -502005 自愈）；`admin.clearUser` 补清 `viewLogs`。
- 降级策略：去重失败只打日志，不阻断详情返回。

### 2. 会话列表分页（chat.convs）

- 原实现：`limit(100)` 无分页，重度用户（>100 会话）被静默截断。
- 后端：`convs({page,pageSize})`，`skip/limit` + 返回 `hasMore`。
- 前端：`chat.js` 加 `page/pageSize/hasMore/loading`，`fetch(reset)` 支持追加，`onReachBottom` + `loadMore` 触底加载。
- WXML 加「加载更多 / 没有更多了」底部态。

## 二、★ 重大发现：收藏/想要功能彻底损坏（我自己上轮引入的 bug）

**现象**：run_all_features.js 的 B1/B2 写流程失败 —— toggleFav/toggleWant 返回 **code=500**，
`msg: "document.set:fail -501007 invalid parameters. 不能更新_id的值"`。

**根因**：上一轮把 toggleFav/toggleWant 重构为 toggleRelation + ensureSet（确定性 _id）时，
**user 云函数的 ensureSet 没有像 chat 版那样 `delete d._id`**。云开发的 doc(id).set() 里 data
**不允许携带 _id 字段**（_id 只能由 doc(id) 指定），于是每次收藏/想要都 500。

**为什么上轮没抓到**：上轮只跑了 verify_order_p0 / verify_hardening（读接口为主）/
verify_campus_isolation，**没跑 run_all_features 的写流程**。
教训：**凡改了云函数写路径，必须跑写流程回归**。

**修复**：user 与 goods 的 ensureSet 统一加 `delete d._id`（与 chat 版对齐），部署后复测 → **59/59 全过**。

**方法论沉淀**：这类「确定性 _id + set」写法在项目里有 3 处（chat/user/goods），行为必须一致 ——
chat 版注释里早就写了「不能再次出现 _id」，说明**先例是有意识的设计**，抄实现时必须连注释里的坑一起抄。

## 三、界面优化：商品卡片「想要」热度（闲鱼式社会证明）

- components/goods-card：卡片底部右侧新增「🔥 N想要」（珊瑚橙，求购商品不展示，0 时不展示避免满屏 0）。
- **实现要点（也是这次最深的坑）**：显示条件**必须放 JS（observers）里算成布尔 showWant**，
  不能写在 WXML 表达式里 —— `wx:if="{{item.type !== 'want' && item.wantCount > 0}}"`
  这种「!== 混 && 混 >」的复杂表达式在 WXML 里**不按预期求值**（数据明明是 sell/5 却不渲染）。
  用组件内 DBG 元素拿到决定性证据（组件实际收到 `T:sell,W:5`）后定位。
- user.myGoods 用 {_openid, ...rest} 解构保留 wantCount，sold 页卡片同样显示热度。

## 四、顺带修复：首页「签名去重」会吞掉内容更新（真实 bug）

index.js 的列表签名只用 _id 序列 → **同 _id、内容变化**（改价/想要数/浏览数）被当成
「数据没变」跳过 setData。实测：卖家改价后首页一直显示旧价。已改为内容签名
（_id|price|status|title|images.length|wantCount|favCount|viewCount），内容不变仍跳过（保留防闪烁优化）。
