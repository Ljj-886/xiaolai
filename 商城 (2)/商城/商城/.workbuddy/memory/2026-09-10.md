### 🔑 关键：automator 接入 IDE 的正确姿势（踩坑很久，务必照做）

**症状**：9420 端口被 IDE 占用，`automator.connect` 却报
`Failed connecting to ws://...:9420, check if target project window is opened with automation enabled`

**根因与解法**：
1. **必须先用 CLI 的 `--auto-port` 启动自动化服务**（不是 `--port`）：
   ```
   & "D:\weixinkaifa\微信web开发者工具\cli.bat" auto --project "D:\商城" --auto-port 9420
   ```
   - `cli open --project` 只开项目窗口，9420 上跑的是 CLI 的 **HTTP server**，automator 握手必失败
   - `--port` 是 HTTP 端口；`--auto-port` 才是自动化 ws 端口（automator.launch 内部就是这么调的）
2. **wsEndpoint 必须用 `ws://localhost:9420`，不能用 `127.0.0.1`**（实测 127.0.0.1 连不上，localhost 可以）
3. **连接是一次性的**：connect 后 `close()` 会让自动化服务失效，下次必须重新 `cli auto --auto-port` 激活
   → 所以不要提前 probe 探测，激活后**立刻**跑正式脚本（一次连接内干完所有事）
4. **不要用 `Automator.launch()`**：它内部用 Node `spawn` 直接跑 `.bat`，Windows 上不可靠
   （报 `Failed to launch wechat web devTools, please make sure cliPath is correctly specified`）

### 🔑 automator 导航 API 失效，改用运行时 wx API


### 修补：publish 超时根因（用户报的 -504003）

**根因**：`seccheck` 云函数首次调用耗时 **2179~2388ms（冷启动）**。
`goods.publish` 里同步嵌套调用它，若 goods 自身也冷启动，两者叠加就会突破 3s 上限 → `-504003`。
这解释了为什么超时是**偶发**的（只在冷启动时出现）。

**修复**：`cloudfunctions/goods/index.js` 给 seccheck 嵌套调用加 `withTimeout(..., 2000, null)` 硬上限，
超时视为「检测未生效」降级放行，绝不拖垮发布主流程。已部署（success true, 11.8 KB）。

### ⚠️ 自动化测试的两个陷阱（我踩了，别再犯）
1. **直接调页面方法会误报**：按钮 handler 需要事件对象 `e`，直接 `cur.method()` 会因
   `e.currentTarget.dataset` undefined 抛 TypeError。要传模拟事件：
   `{ currentTarget:{dataset:{}}, target:{dataset:{}}, detail:{value:''} }`
2. **字段名要核对源码，别猜**：
   - 发布页类型在 `data.form.type`（不是 `data.type`）
   - 详情页想要/收藏在 `data.item.wanted` / `data.item.faved`（不是 `data.wanted`）
3. **连续高频调用会把 automator 拖超时**（表现为 `timeout waiting for automator response` 假阳性）。
   每个云函数操作要单独 evaluate + 充分等待（1.5~3s），别在循环里密集调。
